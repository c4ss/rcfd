# Roadmap overview

rcfd is an early-stage CFD solver that has not been validated for engineering decisions. The counts of roadmap items done, partly done and not started are under [Where it stands](#where-it-stands). FAN-01, the reference fan case, stalls. A structural solver is partly built. One workspace layer for Claude Code and the Studio comes first.

This page is the short, plain-language version of the plan, for anyone who wants to know what rcfd can do today and what comes next. The full list of items, with acceptance criteria, is in [the detailed roadmap](ROADMAP.md). Its list of items is generated from `roadmap.json`, which is the source of truth for every status below. The numbers under "Where it stands" are generated from `roadmap.json`. The hand-written parts of this page were last reviewed on 2026-11-18. To learn how to use rcfd, start at [the documentation home](index.md) instead.

## What rcfd is

rcfd is a finite-volume CFD (computational fluid dynamics) solver written in Rust. It is built clean-room: every algorithm comes from published literature or first principles, with no vendor code, binaries or documentation text. Vendor documentation was consulted in a few recorded cases: mostly contents pages, to list capabilities, and some theory pages, as a check of model constants that are now marked UNVERIFIED. The [provenance record](provenance.md) lists each case. The long-term goal is an open-source toolset that covers what commercial simulation packages do, starting with CFD, so that small teams can build cheap products on top of it.

It is early-stage software. It has not been validated for engineering decisions, and nothing here is certified for safety-critical use.

## What works today

- Incompressible and compressible flow on unstructured meshes, with a range of turbulence models, heat transfer, species transport and particles.
- Mesh import and export in common formats, VTK output, a command-line tool, a scripting API and an MCP server that lets an AI assistant drive the solver.
- A test suite of several thousand tests. The tests a change selects run before it is merged, and the whole suite runs as a [gate](glossary.md) every day. Numeric limits are written down before a run, and a miss is recorded as a known miss, never tuned away.

## What does not work yet

- FAN-01, the reference fan case, stalls. The steady rotating-frame solve of the reference fan does not reach the expected operating point. Several suspected causes have each been ruled out as the single cause, and the diagnosis is open. See [the fan milestone](milestone-fan.md).
- The structural solver is partly built (crate `rcfd-fem`; plan approved on 2026-11-12, ADR 0270, 0290 and 0310). [The structural solver page](structural-solver.md) says what it covers and where its limits are; it has not been validated against a measured case.
- Sliding-mesh transient solves, needed for rotor-stator interaction and broadband noise, are not available.
- The desktop app is being rebuilt. The old egui interface was removed (F-449). The new one (an Electron app in `apps/studio-web`) runs from a checkout, with no installer yet; `docs/tutorials/desktop-assistant.md` shows how to start it.

## What we are working on

### One workspace layer for Claude Code and the Studio

This comes first (set on 2026-11-04). Claude Code can do work through the MCP server that the Studio never sees: some of its tools keep their state in the server's memory and run solves inside it. [ADR 0173](adr/0173-workspace-layer-between-the-project-folder-the-mcp-server-and-the-studio.md) proposes one shared layer, so that every change Claude makes lands in the project folder, goes through one rule for writing files, and shows in the Studio with who made it, what changed and why. Through it, Claude can create cases and run new simulations, and check, draw and import meshes, all inside the project. The work is roadmap items F-270 to F-275.

### Computer fan

The first target is a 120 mm axial computer fan. The aim is a parametric fan that an AI assistant can modify, with predictions of airflow, noise and vibration, and of how they change with manufacturing error and dust build-up. The parts that do not need a converged fan solve are in place: geometry and tolerance tools, a fast reduced-order performance model, rotor-dynamics checks and a design ledger that keeps every variant. The plan and its limits are in [the fan project breakdown](fan-project-breakdown.md). Nothing predicts a real fan better than the measured data it is checked against, and we have none yet.

### Studio, the new desktop application

Studio treats a project as a folder holding many runs. You will be able to play a run back through time, run several in the background, and chat with Claude Code in a side panel, the Studio's only assistant: the local-model assistant of the old egui app was removed (F-838). The libraries underneath exist and are tested without a window: the project format, a background run service and a time-series store. The Studio is an Electron app that draws with three.js (WebGPU, or WebGL 2); see [the Studio plan](ui-restart-plan.md) and ADR 0800.

### Faster tests that stay strict

A full test run takes over an hour. We are adding per-test time limits and a better runner, and checking for tests that can never fail. See [the test process](test-process.md).

## What comes next

1. The workspace layer of ADR 0173 (F-270 to F-275), in the order the ADR sets out.
2. Close the FAN-01 diagnosis, or choose a different reference case for the rotating machinery path.
3. Studio shell and plugin, then 3D rendering of fields and animation.
4. A structural solver, so stress and strain can be shown. Approved on 2026-11-12 and started (ADR 0270, 0290 and 0310).
5. Noise and vibration predictions from a converged fan solution.
6. Validation of the fan models against measured data from a real small fan.

## How you can help

- Measure a small fan. The most useful contribution is data from one real computer fan: its fan curve at several impedances, its sound level and its geometry. [The measurement protocol](fan-measurement-protocol.md) says how.
- Pick up an item that has not started. The detailed roadmap lists them with acceptance criteria. Read the contribution guide in the repository root first, because the clean-room rule is strict.
- Review a result. Each batch of work ends with measured values set against limits written down beforehand. A second look at a limit or a known miss helps.
